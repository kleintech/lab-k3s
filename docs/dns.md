# DNS: how names reach the lab

## The model

| name | answered by | resolves to | who uses it |
|------|-------------|-------------|-------------|
| `*.lab.kleincogroup.com`, `lab.kleincogroup.com` | UDM Pro (LAN only) | `192.168.4.243` (the lab host) | every internal service |
| `<name>.kleincogroup.com` (exposed services only) | Cloudflare, LAN included | Cloudflare edge, then the `homelab` tunnel | services published with `scripts/expose.sh` |
| `<name>` (short LAN names, opt-in) | UDM Pro (LAN only) | `192.168.4.243`; Traefik redirects `http://<name>/` to `https://<name>.lab.kleincogroup.com/` | people typing a bare name on the Wi-Fi |

Traefik on notatonix terminates TLS for both with wildcard Let's Encrypt certs. cert-manager
gets them by DNS-01 through Cloudflare, so the lab never has to be reachable from the
Internet to get a cert. See `CONVENTIONS.md`, "Domain and TLS".

### Why `lab.kleincogroup.com` and not `.local` / `.lan`

- **Certificates.** Let's Encrypt only issues for names under a public suffix that you can
  prove you control. `.local` and made-up TLDs can't get a publicly trusted cert, so every
  browser would show a warning, or every device would need a private CA installed. Under
  `kleincogroup.com` (on Cloudflare), DNS-01 works and the certs are trusted everywhere.
- **mDNS.** `.local` is reserved for multicast DNS (RFC 6762). macOS, iOS and Linux
  (systemd-resolved/Avahi) send `*.local` lookups to mDNS instead of the UDM, so unicast
  records for `.local` resolve unreliably or not at all.
- **No public leak.** Public DNS has no records under `lab.kleincogroup.com`, so the
  internal names resolve only on the LAN. (They do show up in Certificate Transparency
  logs, but only as the wildcard `*.lab.kleincogroup.com`. Individual service names never
  appear.)

### Split horizon

The UDM's resolver (dnsmasq, generated by UniFi OS) answers its own static records first.
Everything else goes upstream (DoH to Cloudflare through `127.0.0.1#5053`). Two records
cover the whole lab:

| record | type | value |
|--------|------|-------|
| `*.lab.kleincogroup.com` | A | `192.168.4.243` |
| `lab.kleincogroup.com`   | A | `192.168.4.243` |

The bare name needs its own record because a `*.` wildcard matches only names *below* it.

Exposed services (`<name>.kleincogroup.com`) get **no** UDM record. See the next section.

### Exposed names and ECH: no split horizon

Until 2026-10-16, `expose.sh` also put `<name>.kleincogroup.com A 192.168.4.243` on the UDM so
LAN clients would skip the tunnel. That breaks Chrome:

- The UDM answers the **A** query itself, but forwards the **HTTPS** (type 65) query upstream.
  Cloudflare's answer carries an `ech=` config (Encrypted ClientHello, on by default for the
  zone, with outer name `cloudflare-ech.com`).
- Chrome sends an ECH ClientHello to 192.168.4.243. Traefik doesn't speak ECH, so it answers
  with the `*.kleincogroup.com` cert. Chrome checks that against `cloudflare-ech.com` and
  fails with `ERR_ECH_FALLBACK_CERTIFICATE_INVALID`.

So exposed names now go through Cloudflare from the LAN too (Access login included), and
`expose.sh` warns if it finds a UDM record for the name. Remove one with
`scripts/udm-dns.sh rm <name>.kleincogroup.com 192.168.4.243` or in the UniFi UI. The LAN
name `<name>.lab.kleincogroup.com` still goes direct: public DNS has no HTTPS record for it.
Turning ECH off for the zone (SSL/TLS → Edge Certificates; the lab's API token can't) would
also fix it, at the cost of ECH for every public visitor.

## Short LAN names (`http://pool/`)

For a guest on the Wi-Fi, typing `pool` beats `pool.lab.kleincogroup.com`. No publicly
trusted certificate can cover a bare name, so the short name only ever answers **plain
HTTP** and only to redirect to the real HTTPS name:

1. **UDM record** `pool A 192.168.4.243` (`scripts/udm-dns.sh set pool 192.168.4.243`, or
   the UniFi UI). The DHCP leases carry no search domain, so clients look up the bare name
   as-is, and the UDM's dnsmasq answers it.
2. **Traefik route** in the app's own manifests: an `IngressRoute` on entrypoint `web`, rule
   ``Host(`pool`)``, **priority above 10000**, with a `redirectRegex` Middleware to
   `https://pool.lab.kleincogroup.com/...`. The `web` entrypoint's blanket HTTP→HTTPS
   redirect runs at priority 10000 (see `platform/traefik/manifests/helmchartconfig.yaml`),
   so without the higher priority the request is sent to `https://pool/` and fails the cert
   check. Give it `entryPoints: [web]`, or it also attaches to websecure. kleintech/jandy-home-webui's
   `k8s/short-name.yaml` is the worked example.

**Order matters: route first, DNS record last.** Until the route above is live, `http://pool/`
gets the blanket redirect, which is a **permanent** 301 to `https://pool/`. Browsers cache
that indefinitely and never ask `http://pool/` again, so a device that tried early stays
broken after the route ships. Before adding the UDM record, check the route answers:

```
curl -sI -H 'Host: pool' http://192.168.4.243/   # -> 302, Location: https://pool.lab.kleincogroup.com/
```

What the user has to type depends on the browser. Most treat a bare word as a search:

- Chrome / Edge / Firefox: `pool/` (or `http://pool`) goes straight there. Plain `pool`
  searches; Chrome then offers "Did you mean http://pool/?".
- Safari (iOS and macOS): `pool/` or `http://pool`.

Bookmarks, a home-screen icon, or a QR code on the Wi-Fi card avoid typing altogether.
Check from a LAN client: `curl -sI http://pool/` should return a redirect to
`https://pool.lab.kleincogroup.com/`.

## Managing the records: `scripts/udm-dns.sh`

```
scripts/udm-dns.sh list
scripts/udm-dns.sh ensure-lab                     # the two lab records above
scripts/udm-dns.sh set pool 192.168.4.243         # a short LAN name (see "Short LAN names")
scripts/udm-dns.sh rm  foo.kleincogroup.com [192.168.4.243]   # optional: only records with that value
scripts/udm-dns.sh -n ...                         # dry run: print DNS writes, don't send them
                                                  # (with user/password it still logs in and out)
```

`set` is an upsert: it creates the record, changes its IP or re-enables it, or does nothing
if it's already right. If a name already has several A records, or a CNAME, `set` refuses
to pick one for you. After every write, the script checks the result with
`dig @192.168.4.1` (5 tries). For a wildcard it queries `udm-dns-probe.<rest>`.

### Credentials: `~/.config/lab-k3s/udm.env` (chmod 600, never in git)

```
UDM_HOST=192.168.4.1
# Either an API key (preferred):
UDM_API_KEY=...
# or a local UniFi OS admin account (no 2FA, not an SSO/ui.com account):
UDM_USER=...
UDM_PASS=...
```

- **API key:** create one in the Network app under **Settings → Control Plane →
  Integrations**. "Control Plane" is in the 10.6.106 UI strings. "Integrations" is not in
  the Network app's strings and may sit in the UniFi OS console settings instead. With a
  key, the script uses the
  documented **UniFi Network API** (`/proxy/network/integration/v1/sites/{siteId}/dns/policies`,
  header `X-API-KEY`).
- **User/password:** the script logs in with `POST /api/auth/login`, keeps the session
  cookie and `X-CSRF-Token` in a private temp dir (deleted on exit), and uses the endpoint
  the web UI itself uses: `/proxy/network/v2/api/site/default/static-dns`. Records there
  are `{"_id", "key", "record_type": "A", "value", "enabled", "ttl"?}`. `POST` creates,
  `PUT .../{_id}` updates, `DELETE .../{_id}` deletes.
- Force a backend with `UDM_API=integration` or `UDM_API=v2`. With `UDM_API=v2` and a key
  set, the key is sent to the v2 endpoint. That combination is **unverified** (see below).
  If it is rejected, the script says so.
- TLS: the UDM's certificate is self-signed, so the script uses `--insecure` unless you set
  `UDM_CACERT=/path/to/ca.pem`. The script talks only to `UDM_HOST` on the LAN.

### What has been verified (2026-10-07, UniFi OS 5.1.33, Network 10.6.106)

Verified read-only on the UDM itself:

- `/proxy/network/v2/api/site/default/static-dns` exists. Network's backend (`:8081`)
  answers it with `401 api.err.UserNotAuthenticated`, and a nonexistent sibling path with
  `404`. The binary also defines `/api/site/{siteName}/static-dns/{id}`.
- The record shape (`key`, `record_type`, `value`, `enabled`, `ttl`, `_id` as the id field)
  and PUT-to-`/{id}` for updates come from the Network web UI bundle that ships on the UDM.
- The web UI's domain validator is `^(\*\.)?([\w-]+\.)*[\w-]+\.?$`, so a leading `*.`
  wildcard is accepted.
- The UDM ships an OpenAPI spec (`/usr/lib/unifi/webapps/ROOT/api-docs/integration.json`,
  "UniFi Network API" 10.6.106). It defines `GET/POST /v1/sites/{siteId}/dns/policies`
  and `GET/PUT/DELETE .../{dnsPolicyId}`. An A record there is
  `{"type":"A_RECORD","enabled":true,"domain":"...","ipv4Address":"...","ttlSeconds":N}`.
- UniFi OS's nginx runs the same auth subrequest for every `/proxy/network/` path, and that
  subrequest understands `X-API-Key` (it forwards an `X-ApiKeyId`).
- Wildcard records do work in this dnsmasq: the generated config already contains
  `address=/*.devices.wifiman.me/192.168.1.1`.

Not verified (no credentials were available to the author):

- An actual write through either backend.
- Whether the **integration API accepts a `*.` wildcard** in `domain`. If it returns 400 for
  `*.lab.kleincogroup.com`, use user/password credentials (`UDM_API=v2`) for `ensure-lab`.
- Whether the v2 `static-dns` endpoint accepts an **API key** instead of a session.
- How UniFi renders a wildcard static record into dnsmasq. The `dig` check after each write
  is the test.
- Whether either API accepts a **single-label** name like `pool` (the web UI's validator
  does). If one returns 400, add it in the UniFi UI.

## Fallback: add the records in the UniFi UI

No API credential at all? `scripts/udm-dns-mongo.sh` writes the two lab records over root SSH
(mongo `static_dns` + Network app restart); it is what was used on 2026-10-07 when no API key existed.

In Network 10.x, DNS records live in the Policy Engine. On 10.6.106 the screen labels are:
**Settings → Policy Engine → Policy Table → Create New Policy → DNS Record**. Older 8.x/9.x
builds had them under *Settings → Routing → DNS*. Create:

- Type **A**, Domain Name `*.lab.kleincogroup.com`, IP `192.168.4.243`, TTL Auto
- Type **A**, Domain Name `lab.kleincogroup.com`, IP `192.168.4.243`, TTL Auto

The labels were read from the 10.6.106 UI bundle on the UDM, not clicked through. If the
menu has moved, search the settings for "DNS Records".

Check from any LAN client:

```
dig +short anything.lab.kleincogroup.com @192.168.4.1   # -> 192.168.4.243
dig +short lab.kleincogroup.com @192.168.4.1            # -> 192.168.4.243
```

## VLANs: who can reach 192.168.4.243

The UDM serves DNS on every LAN network, so clients on every VLAN *resolve* the lab names.
Whether they can *connect* is a firewall question, and that is deliberately not documented
here. How to check after any firewall change:

- UI: **Settings → Security → Firewall** (legacy rules), or **Zone-Based Firewall /
  Policy Table** after a migration. Look for rules dropping traffic to the lab host's
  network, and for **Network Isolation** on the source network.
- From a client on that VLAN:
  `curl -sI https://whoami.lab.kleincogroup.com` should return HTTP 200. If you get a
  timeout while `dig` still answers 192.168.4.243, the firewall is in the way, not DNS.

If a VLAN is isolated, either allow it to reach `192.168.4.243` TCP 80/443, or have those
users go through the public `<name>.kleincogroup.com` names (tunnel). The registry and the
Traefik dashboard additionally carry a source-IP allow-list (`lan-only` Middlewares), which
is the place to add or remove a subnet.

## Off the LAN

`*.lab.kleincogroup.com` is intentionally unreachable from outside. Options:

1. **Publish one service** with `scripts/expose.sh <name> --public|--gated`. It becomes
   `https://<name>.kleincogroup.com` via the Cloudflare tunnel, optionally behind
   Cloudflare Access. See [cloudflare.md](cloudflare.md).
2. **A VPN into the LAN** whose clients use the UDM as resolver; the lab names then work as
   on the LAN (check with `dig lab.kleincogroup.com` while connected).

## Troubleshooting

- `dig @192.168.4.1` is right but the browser fails: the browser may be using its own
  DNS-over-HTTPS (Firefox "DNS over HTTPS", Chrome "Use secure DNS" with a custom provider).
  That skips the UDM, so `*.lab` doesn't exist for it. Turn that off for the LAN, or add an
  exception.
- A name was just added and doesn't resolve: dnsmasq picks up changes when UniFi re-renders
  its config, usually within seconds. `scripts/udm-dns.sh` retries the `dig` 5 times. A
  client may also have cached the earlier NXDOMAIN (macOS:
  `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`).
